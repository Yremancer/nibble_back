# nibble_back — правила для AI-агентов

Единый файл правил для всех агентов (Claude Code, Cursor, Codex и др.).
Менять через PR. Держать коротким: длинное выносить в скиллы (`.agents/skills/`).

## Проект
- Бэкенд: FastAPI + SQLAlchemy 2 (async) + Alembic + PostgreSQL, всё в Docker.
- Код: `backend/src/`. Миграции: `backend/migrations/`.
- Конфиг через `.env` (шаблон `.env.example`). Секреты и `.env` не коммитить и не читать вслух.

## Архитектура: модульный монолит
Одно FastAPI-приложение, код сгруппирован по предметным модулям; внутри модуля разделены HTTP-слой, бизнес-логика и работа с БД.

```
backend/src/
├── app.py           сборка приложения, роутеры, CORS, обработчики ошибок, старт/остановка общих клиентов
├── settings.py      настройки из .env
├── exceptions.py    общие базовые ошибки
├── exc_handler.py   ошибки приложения → HTTP-ответы
├── <модуль>/        предметные модули
├── database/        движок, сессия, Base, общий список моделей для Alembic
├── storage/         файлы: содержимое в S3-совместимом хранилище, метаданные в PostgreSQL
└── utils/           мелкие общие функции
```

Модуль (файлы только те, что ему нужны; узкая логика — в отдельных файлах, например `source/telegram.py`):

| Файл | Что делает |
| --- | --- |
| `router.py` | Эндпоинты: принимает данные по схемам, вызывает сервис, возвращает ответ. Без бизнес-логики. |
| `schemas.py` | Pydantic-схемы входа и ответа. |
| `service.py` | Сценарии и правила: что проверить, что сделать, в каком порядке. Может звать несколько репозиториев, сервисов и клиентов. |
| `repository.py` | Весь SQL через SQLAlchemy: выборки, вставка, изменение, удаление. |
| `models.py` | ORM-модели модуля. |
| `exceptions.py` | Ошибки модуля (не найдено, запрещено состоянием объекта), наследники `src/exceptions.py`. |
| `deps.py` | Сборка через `Depends`: сессия → репозиторий → сервис → роутер. |
| `client.py` | Только у внешних интеграций: сам вызов API/SDK и перевод его ошибок в ошибки приложения. |

Путь запроса: `router` → `service` → `repository` → PostgreSQL; результат → схема ответа → HTTP.

Правила:
- Транзакцией управляет зависимость сессии (`session.begin()` в `database/database.py`): репозитории делают `flush()`, не `commit()`.
- Сервисы бросают ошибки модуля, в HTTP их переводит `exc_handler.py`. `HTTPException` из сервисов не бросать.
- Внешние API (погода, Telegram, VK, S3) — клиент только вызывает, сценарии в сервисе. Общие подключения (`httpx.AsyncClient`, S3) создаются при старте в `app.py` и закрываются при остановке.
- Модули могут использовать сервисы и репозитории друг друга.
- Каждая ORM-модель должна попасть в общий список, который импортирует `migrations/env.py`, иначе Alembic её не увидит.

## Команды (из корня, через Makefile)
- `make start` — поднять backend+db и применить миграции
- `make rebuild` — снести тома и пересобрать (удаляет данные БД!)
- `make new-migr name="..."` — создать миграцию; `make update-db` — применить
- `make see-api` — логи; `make see-db` — psql
- Python запускать внутри контейнера (`docker compose exec backend ...`), не на хосте.

## Правила
- Ветки: работаем в `dev`, `main` обновляется только через `make merge`. Не пушить в `main` напрямую.
- Любое изменение моделей — только вместе с миграцией Alembic. Миграции не править задним числом.
- Минимальный diff: решать задачу, не рефакторить попутно и не добавлять зависимости без причины.
- Асинхронный код: не использовать блокирующие вызовы в `async`-путях.
- Не выполнять разрушительные действия (`down -v`, `rebuild`, drop, force-push) без явного согласия человека.
- Коммиты — Conventional Commits (`feat:`, `fix:`, `chore:`), коротко, по сути.
- Агент не указывает себя автором: никаких `Co-Authored-By`, `Generated with` и подобных строк в коммитах, PR и документации. Автор — человек, который коммитит.

## Комментарии и смайлики
- Комментарии только там, где неочевидно ПОЧЕМУ (обход бага, ограничение, неочевидное решение). Не пересказывать код, не оставлять закомментированный код, не писать «TODO» без причины и автора.
- Не добавлять докстринги и комментарии к коду, который не менялся.
- Смайлики и эмодзи запрещены везде: в коде, комментариях, логах, ответах API, коммитах, PR, документации и в ответах пользователю.

## Обязательные навыки

Навыки указаны по имени, а не по пути к чьему-то компьютеру или агенту. Найди навык так:
1. если он уже установлен у тебя (в глобальных или проектных навыках твоего агента) — используй его;
2. иначе открой копию из репозитория: `.agents/skills/<имя>/SKILL.md` (общая копия для всех; для Claude Code выполни `make skills` — копия попадёт в `.claude/skills/`, в git она не идёт).

| Навык | Когда применять |
| --- | --- |
| `ponytail` | Любая работа с кодом бэкенда: фиксы, рефакторинг, ревью, выбор зависимостей, миграции |
| `caveman` | Общение с пользователем: кратко, по делу, без потери смысла |

- Перед первой правкой кода применяй `ponytail`, перед первым ответом пользователю — `caveman`. Остальные навыки подключай по их описанию.
- Для бэка: сначала то, что уже есть в `backend/src/` и в stdlib/FastAPI/SQLAlchemy, и только потом новая зависимость или абстракция.
- Не вписывать в этот файл абсолютные пути (`C:/Users/...`, `/Users/...`) и пути, специфичные для одного агента.
- Новые навыки — только через PR после чтения `SKILL.md`; источник и коммит фиксировать в `.agents/skills/SOURCES.md`.

## Окружение (Windows + macOS)
- В команде есть Windows и macOS: не писать пути с `C:\`, не полагаться на симлинки, на регистр имён файлов и на конкретный shell.
- Команды запускать через `make` и Docker (Makefile сам выбирает `sleep`/`timeout` под ОС).
- Файлы — UTF-8, переводы строк LF. Не коммитить `.DS_Store`.
