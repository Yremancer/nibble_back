# nibble_back

FastAPI, PostgreSQL и агрегатор. Команды выполняются из корня репозитория через Make и Docker Compose.

## Установка

1. Скопируйте `.env.example` в `.env`. Заполните `DB_PASSWORD`; оставьте `DB_HOST=db` для Docker.
2. Для хранилища задайте `S3_ENDPOINT_URL`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, при необходимости `S3_REGION`. Пустой endpoint означает AWS S3. Старые имена `S3_ACCESS_KEY` и `S3_SECRET_KEY` не используются.
3. Для агрегатора задайте `DEEPSEEK_API_KEY`. Публичные Telegram-каналы читаются через `https://t.me/s/<username>` без ключей и авторизации: оставьте `TELEGRAM_API_ID=0` и пустой `TELEGRAM_API_HASH`.
4. Выполните `make start`. Команда пересобирает backend, поднимает PostgreSQL и применяет миграции. API: `http://localhost:8000/docs` при стандартном порте.
5. Только для доступа через Telethon: задайте `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, при желании `TELEGRAM_PHONE`, выполните `make auth-telegram` и введите код Telegram, при необходимости пароль 2FA. Для публичного веб-превью этот шаг пропускается.
6. Выполните `make doctor`.

Активные Telegram-каналы задаются в `backend/src/aggregator/sources.json` (`is_active=true`). Без API credentials нужны открытые каналы с username и доступным веб-превью. Диагностика проверяет чтение каждого канала выбранным способом. Для закрытого канала нужны Telethon и доступ аккаунта сессии.

Режим без ключей сохраняет текст, дату, ссылки, публичные счётчики и доступные в превью фото/видео, включая альбомы. Прямые ссылки на медиа обновляются перед скачиванием. Первый `sync` загружает недавние посты за `AGG_RECHECK_WINDOW_HOURS`, следующие продолжают с курсора. Историю можно загрузить командой `docker compose exec -T backend python -m src.aggregator.cli backfill --source telegram --since 2026-11-01`; без `--since` глубина веб-сбора ограничена `AGG_BACKFILL_DEPTH_DAYS`. Публикации и вложения, скрытые в веб-превью, недоступны; точная дата редактирования не предоставляется. Разметка Telegram может измениться и потребовать обновления парсера.

Для ручной проверки: `GET /aggregator/telegram?channel=ulov25r&limit=5`. Параметр `channel` — обязательный username без `@`; `limit` — от 1 до 50, по умолчанию 5. Ответ содержит последние посты от новых к старым с текстом, датой, ссылкой на публикацию и списком `media` (прямой `url` и `media_type`: `photo` или `video`). Альбом считается одним постом. Как и `GET /aggregator/farpost`, ручка не записывает данные в БД, не вызывает LLM и не загружает файлы в S3. Доступна в Swagger; недоступный канал или ошибка Telegram возвращают 502.

`TELEGRAM_SESSION_PATH=/app/data/telegram.session` соответствует `backend/data/telegram.session` на хосте благодаря bind mount. Каталог создаётся автоматически при авторизации, диагностике и синхронизации. Файлы сессии и SQLite journal/WAL исключены из Git и контекста сборки Docker. При смене пути сохраняйте его внутри постоянного mount.

`doctor` проверяет версию Alembic, доступность всех таблиц и колонок ORM, Telegram-сессию и активные каналы, тестовый ответ DeepSeek, запись/чтение/удаление временного объекта S3. Доменные данные он не записывает. Запрос DeepSeek расходует API-квоту. Код CLI: `0` — всё готово, `1` — есть обязательная неисправность. `make doctor` также возвращает ненулевой код при ошибке. Без активных каналов Telegram пропускается; DeepSeek и S3 нужны для полного конвейера, их отсутствие считается ошибкой.

## Обновление существующей БД

Перед обновлением выполните `make dump`: SQL-копия появится в `dumps/`. Не используйте `make rebuild` для обновления: эта команда удаляет том PostgreSQL.

Каталог `dumps/` подключён только для ручного резервного копирования и восстановления. PostgreSQL не загружает его содержимое при чистой установке. Для переноса plain SQL-дампа между окружениями создавайте его с `pg_dump --no-owner --no-privileges`, чтобы восстановление не зависело от имён ролей исходного сервера.

Миграция `c6e84a12d903` исправлена до её применения в локальном окружении. Она блокирует изменяемые таблицы на время транзакции, переносит метаданные из `media_files` в `files`, строит соответствие старых и новых ID, обновляет `post_media`, `listing_media`, `agg_media_attachments`, затем переключает FK и удаляет старую таблицу. Совпадающий числовой ID не означает совпадающий файл. Существующая запись `files` переиспользуется только по S3-ключу с совпадающими размером и MIME. `NULL`-связи сохраняются, последовательность ID обновляется.

Объекты S3 остаются на прежних ключах. Все записи `media_files.bucket` должны соответствовать `S3_BUCKET`. Другой bucket, повторяющиеся `object_key`, конфликт метаданных или размер вне диапазона `files.size` останавливают обновление с откатом транзакции. Сначала устраните указанную причину; для другого bucket перенесите объекты и проверьте их до изменения метаданных.

Проверка обновления на копии работающей БД:

```sh
make dump
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc -f /dumps/before-shared-files.dump'
docker compose exec -T db sh -c 'createdb -U "$POSTGRES_USER" nibble_upgrade_check && pg_restore -U "$POSTGRES_USER" -d nibble_upgrade_check --exit-on-error /dumps/before-shared-files.dump'
docker compose build backend
docker compose run --rm --no-deps -e DB_NAME=nibble_upgrade_check backend alembic upgrade head
docker compose run --rm --no-deps -e DB_NAME=nibble_upgrade_check backend pytest -q
```

Используйте свободное имя проверочной БД. Тесты миграции создают и удаляют собственные временные БД; тестовому пользователю нужно право `CREATEDB`. Остальные DB-тесты откатывают свои транзакции. После проверки выполните `make start` и `make doctor` для основного окружения.

Откат этой миграции при наличии связанных файлов намеренно запрещён: старая схема не может восстановить утраченные SHA256 и другие поля. Для возврата используйте копию БД и соответствующую ей версию кода. Если прежний вариант `c6e84a12d903` уже применили к заполненной БД, правильные старые связи нужно восстанавливать из копии до миграции; повторный `upgrade` их не восстановит.

## Очередь агрегатора

`sync` и `backfill` обрабатывают все доступные задачи пакетами по 200 записей. Порядок этапов: normalize, classify, resolve, media, dedup, publish. Дедупликация учитывает загруженные файлы и записи текущей пачки. Спорные совпадения получают статус `moderation`.

Для постоянной обработки очереди запустите в отдельном процессе:

```sh
make worker
```

Для автоматического сбора новых публикаций и повторов включите сервис расписания:

```sh
make schedule
make see-aggregator
docker compose exec -T backend python -m src.aggregator.cli status
```

`aggregator` — один процесс в отдельном контейнере с `restart: unless-stopped`. Он синхронизирует активные Telegram-каналы каждые `AGG_SYNC_INTERVAL_S` секунд (по умолчанию 300), а готовые повторы проверяет каждые 5 секунд. Один проход завершается до начала следующего; общая блокировка PostgreSQL запрещает наложение с ручными командами. Причины сбоев и статистика видны в логах и `status`/`AggRun`. `make start` также поднимает расписание. После изменения `.env` снова выполните `make schedule`: простой `restart` не обновляет переменные окружения.

Первую проверку можно ограничить одним каналом: `docker compose exec -T backend python -m src.aggregator.cli sync --source telegram --channel ulov25r --limit 2`. Для второго канала укажите `nhnc125`. История использует отдельный курсор: `backfill --source telegram --channel ulov25r --since 2026-11-09 --limit 2`.

Worker проверяет очередь каждые 5 секунд. Ошибки повторяются автоматически: максимум 5 попыток, задержки между попытками — 30, 60, 120 и 240 секунд. После исчерпания лимита задача остаётся `failed`. `retry-failed --stage <этап> --limit 100` сбрасывает счётчик выбранных ошибок и запускает конвейер. Без worker отложенные задачи подбирает следующий `sync` или `backfill`.

`reprocess --stage <этап> --limit 100` заново ставит выбранные задачи, включая завершённые, и запускает конвейер. Для `normalize` выбираются сырые Telegram-публикации; последующие этапы запускаются автоматически. Классификация использует кеш по версии содержимого, модели и промпта. Команды CLI выполняются внутри backend: `docker compose exec -T backend python -m src.aggregator.cli ...`.

Захват задач, запись результата и следующий этап фиксируются одной транзакцией на пакет. Ошибка отдельной записи откатывает её savepoint. При остановке процесса незавершённый пакет откатывается; следующий запуск подбирает его снова. Сохранившиеся старые `in_progress` также доступны для обработки. Идемпотентные ключи постов, объявлений и файлов предотвращают повторное создание записей.

`AggRun` хранит источник, команду, результат и статистику запуска. Следующая команда отмечает прерванные запуски как `failed`. Блокировка PostgreSQL не допускает одновременной работы команд с одной Telegram-сессией; для `sync` во время работающего worker дождитесь освобождения блокировки или остановите worker.

Миграция `d71a942bc603` добавляет минимальные справочники: шесть видов рыбы, шесть способов ловли и бухту Аякс во Владивостоке. Существующие записи сохраняются; изображения рыб пока не заданы. При повторном импорте очищаются исчезнувшие уловы, медиа и поля. Ключи в `managed_fields`, включая `catches`/`species` и `media`, сохраняют ручные правки.

## Farpost

Farpost запускается отдельно от Telegram-расписания:

```sh
docker compose exec -T backend python -m src.aggregator.cli sync --source farpost --pages 2 --limit 5
```

`FARPOST_REQUEST_DELAY_S` (по умолчанию 1.5) задаёт задержку между HTTP-запросами списка и карточек, включая редиректы, и перед скачиванием каждого вложения Farpost. Каждый обход сначала проверяет `FARPOST_RECHECK_PAGES` свежих страниц (по умолчанию 2), затем продолжает историю с курсора. `--pages` ограничивает суммарное число страниц за запуск. HTTP 403/429/503, CAPTCHA и сетевые ошибки останавливают обход, сохраняя уже принятые записи. Неизвестная разметка фиксируется как ошибка. Город определяется по карточке или известному городу в URL; неизвестный город не заменяется первым городом справочника.

Если сбор недоступен, сохраните вручную собранные объявления в `backend/data/listings.json` или `.csv` и запустите:

```sh
docker compose exec -T backend python -m src.aggregator.cli import-listings --input /app/data/listings.json --city Владивосток
```

Обязательные поля: `farpost_id` (строка), `title`, `url` на farpost.ru. Минимальный шаблон JSON:

```json
[
  {
    "farpost_id": "123456789",
    "title": "Название объявления",
    "url": "https://www.farpost.ru/vladivostok/example-123456789.html",
    "city": "Владивосток",
    "price_rub": 2500,
    "description": "Описание из объявления",
    "photo_urls": []
  }
]
```

Для CSV первая строка содержит названия тех же полей; несколько `photo_urls` разделяются `;`. Также поддерживаются `price_raw`, `category`, `seller_name`, `seller_url`, `characteristics` (JSON-объект) и `state` (`active`, `removed`, `expired`, `unknown`). Ошибка строки не откатывает остальные. Повторный импорт обновляет запись по `farpost_id`, а исчезнувшие фотографии и характеристики очищаются. Объявления без фотографий публикуются без обращения к S3.

## Проверки

```sh
docker compose exec -T backend pytest -q
make doctor
```

Тесты проверяют новую установку, перенос всех трёх типов связей, конфликт и перестановку ID, переиспользование S3-ключа, большие старые ID, `NULL`, последовательность новых ID и откат небезопасного обновления. Внешние интеграции в тестах `doctor` подменены; реальную доступность проверяет `make doctor` после настройки credentials.
